# 保存与同步

## 一次保存的边界

浏览器提交 `{ ownerId, revision, command }`。服务端先检查来源和会话，再验证页面所属账号与请求格式。在数据库事务中锁定当前用户账本行，读取快照并比较 revision；版本一致才应用命令，保存差异并递增 revision。交易、分录、分类、导入批次和去重标识均在同一事务内提交。

因此同一账本写入串行化，不同用户有独立版本锁。普通交易的修改与删除必须使用本账本已有的对象；业务规则仍由服务端重新执行。客户端等待保存成功后才替换界面快照，同一浏览器状态同时只允许一个保存。

## 冲突与失败处理

| 结果 | 当前行为与处理 |
| --- | --- |
| 版本冲突，HTTP 409 且带 `book` | 返回并加载当前账本；保留填写，用户核对后重新保存，不自动重放 |
| 账号不一致，HTTP 409、`account_changed` | 清空账目和相关工作区、导入历史、弹窗与草稿，阻止旧页面继续保存；刷新重新打开 |
| 会话失效，HTTP 401 | 提示重新登录，保存时填写内容保留 |
| 网络中断或其他保存结果不确定 | 数据库可能已经提交；保留填写并刷新核对，再决定是否提交 |
| 刷新失败 | 显示上次载入的账目并提示同步异常 |

不要把“界面没有收到成功”理解为“数据库一定没有保存”。导入的批次编号另有重试保护，但仍须先处理 revision 检查，详见[账单导入](bill-import.md)。

## 条件刷新

真实账本每 30 秒在页面可见时刷新，窗口获得焦点、页面回到前台也会检查。GET 携带由用户 ID 和 revision 组成的 ETag，服务端相同版本返回 304；变化时返回完整账本。读取在 repeatable read 只读事务内完成，使 ETag 与正文属于同一快照；响应使用 private、no-store 和 Vary: Cookie。

开始保存即令此前刷新失效，即使保存最终失败也如此；正文解析结束后再次检查刷新是否仍有效。刷新不接受比当前 revision 更旧的快照，也不并行刷新。这样可防止旧请求覆盖新保存结果，但它不是后台实时推送。

账号切换保护不仅依赖写入：刷新得到不同 ownerId 也清空私有数据。`BookApp` 随之清除派生工作区状态。
